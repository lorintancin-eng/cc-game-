# MythSurvivor 技术架构

## 技术基线

- 游戏引擎：Godot 4.x。
- 游戏维度：2D。
- 编程语言：GDScript。
- 项目类型：俯视角自动战斗 Roguelite 生存游戏。

架构应优先使用小型场景、职责明确的脚本、Godot 信号和数据驱动资源。玩法代码应保持易读、易调试、易调校。

## 高层运行流程

```text
启动
  -> 主场景
  -> 单局初始化
  -> 玩法场景
  -> 刷怪 / 战斗 / 经验 / 升级循环
  -> 游戏结束或胜利状态
  -> 结算 / 重新开始
```

## 模块边界

### 核心模块

负责共享运行时服务和高层状态。

后续可能负责：

- 单局状态。
- 场景切换。
- 必要时的事件总线或信号路由。
- 全局常量。
- MVP 之后的存档或设置接入。

### 玩法模块

负责当前单局的运行循环。

后续可能负责：

- 游戏会话编排。
- 单局计时。
- 刷怪调度。
- 胜利和失败条件。
- 暂停与恢复协调。

### 角色模块

负责世界中的可移动实体。

后续可能负责：

- 玩家角色。
- 敌人角色。
- 需要时的命中盒与受击盒。
- 移动控制器。
- 角色生命值与死亡信号。

### 战斗模块

负责伤害传递和自动武器行为。

后续可能负责：

- 武器控制器。
- 投射物或范围效果。
- 伤害数据。
- 目标选择。
- 战斗属性修正。

战斗模块不应直接负责升级选择 UI 或永久成长。

### 成长模块

负责单局成长。

后续可能负责：

- 经验收集。
- 等级阈值。
- 升级池。
- 升级应用。
- 未来的局外成长。

成长模块应通过清晰 API 或信号修改玩法状态，而不是任意深入访问其他节点。

### UI 模块

负责面向玩家的界面。

后续可能负责：

- HUD。
- 升级选择。
- 暂停菜单。
- 游戏结束界面。
- 结算界面。

UI 应展示玩法状态，但不应包含核心玩法逻辑。

### 资源模块

负责数据配置。

后续可能负责：

- 敌人定义。
- 武器定义。
- 升级定义。
- 波次定义。
- 掉落定义。

优先使用 Godot `Resource` 类型或结构化数据文件，不要把大量内容表硬编码在玩法脚本中。

## 场景归属规则

- 场景应表示具体运行时对象或界面。
- 脚本只应挂载在其真正负责行为的场景上。
- 不要把多个无关管理器堆在同一个节点上。
- 避免跨场景使用脆弱的深层 `get_node()` 路径。
- 根据情况优先使用导出的 `NodePath`、类型化引用、分组或信号。

## 信号与数据流规则

- 多个系统需要观察的状态变化应使用信号，例如角色死亡、升级、波次变化或单局结束。
- 信号名称应具体。报告已完成事件时，优先使用类似 `enemy_defeated` 或 `upgrade_selected` 的过去式含义。
- 在出现真实共享归属需求前，避免引入全局单例。
- 如果后续引入单例，必须记录它存在的原因和拥有的职责。

## 数据驱动设计

内容密集型系统应尽量通过配置扩展，而不是修改核心逻辑：

- 敌人的最大生命、速度、伤害、掉落表和行为类型。
- 武器的冷却、基础伤害、目标模式、投射物数量、范围和生命周期。
- 升级的标签、属性修正、前置条件和展示文本。
- 波次的时间、生成组合和压力增长规则。

MVP 的任何数值都不得复制商业游戏。平衡必须原创，并通过本地试玩调整。

## 性能方向

- 预期屏幕上会出现大量敌人和投射物。
- MVP 阶段使用简单碰撞形状。
- 在高频路径中避免不必要的逐帧分配。
- 只有在性能分析显示生成/销毁开销明显时，才引入对象池。
- UI 更新尽量由事件驱动，避免每帧刷新所有标签。

## 测试与验证

后续实现任务应验证：

- Godot 项目打开时没有场景或脚本错误。
- GDScript 能正常解析。
- 主场景可以启动。
- 玩家可以完成 MVP 循环。
- 敌人生成和战斗在较高负载下仍然稳定。

当项目中出现足够稳定的逻辑后，再考虑加入自动化测试。

## 当前阶段限制

本文档只定义预期架构。当前文档任务中，不要创建玩法场景、玩家脚本、敌人脚本、武器脚本、升级脚本或运行时管理器。
